## 5. 技術設計

### 5-1. 全体アーキテクチャ — 準備工程と実行時の分離

既存 `index.html` は「1枚の完成写真のピクセルを実行時に分類して色を差し替える」方式だが、実行時の自動分類は撮影条件に強く依存する。今回はチャームが**固定7種**なので、品質が不安定な処理はすべて**準備工程**に寄せ、**人が目視検証してからコミット**する。

```
【準備工程】（tools/charm-prep.html を使い、フェーズ0で1回だけ実施。成果物をコミット）
   元写真 → 背景除去（前景マットα生成）→ defringe（背景色かぶり除去）
         → 所有権マスク生成（革/金具/ステッチ、自動候補＋手動補正）
         → 検証ビュー（暗色背景合成・恒等式検査・マスクオーバーレイ）
         → 派生アセット書き出し: {charm}.base.png ＋ {charm}.masks.png ＋ 定義値

【実行時】（charms.html。ピクセル走査はリカラーのみ）
   派生アセットをロード → リカラー（革=photoLeatherTone / 金具=metalTone / ステッチ=白黒塗り）
         → チャーム完成ビットマップ（チャーム×色×金具×ステッチでキャッシュ）
         → mm基準ステージに丸カン＋左右チャームを実寸比率で drawImage 合成
```

- 実行時に背景除去・マスク生成を行わないため、端末差・初回遅延・誤検出のリスクを排除できる
- 実行時生成方式（旧案）は採用しない。将来チャームが大幅に増えて事前生成が回らなくなった場合にのみ再検討する

### 5-2. 派生アセットとチャーム定義テーブルの契約

**ファイル構成**

```
assets/charms/
  horse.base.png             … 表示用前景画像（RGBA、背景除去＋defringe済み、長辺≤1200pxに正規化）
  horse.masks.png            … 所有権マスク（RGB: R=革 / G=金具 / B=ステッチ。baseと同寸）
  horse.prep.json            … 準備工程の再現データ（§5-4。実行時は読まない）
  horse.manual-alpha.png     … 手動補正レイヤ①: 前景マット強制（同寸。実行時は読まない）
  horse.manual-owner.png     … 手動補正レイヤ②: 所有権強制（同寸。実行時は読まない）
  horse.manual-inpaint.png   … 手動補正レイヤ③: base.RGB置換（fallback元糸中和等。同寸。実行時は読まない）
  …（7種 × 一式。手動補正が無いレイヤのファイルは省略可）
assets/rings/
  ring-silver.png / ring-gold.png … 丸カン透過PNG（準備工程で生成。42mm外径の共通基準枠に正規化・中心一致）
source-photos/               … 受領した元写真（再生成用に保存）
tools/charm-prep.html        … 派生アセット生成・検証ツール
```

**base.png（前景マット）の契約**

- α = 前景マット（0–255）。エッジは1–2pxのフェザー
- **defringe 必須**: α<255 の画素の RGB は最近傍の不透明画素色で置換し、JPEG背景（白系）の色かぶりを除去する
- 検証: 暗色背景（#333）と明色背景（#eee）の両方に合成し、輪郭に白/黒のハロが出ないこと（準備ツールの検証ビューで目視＋エッジ帯の彩度異常の自動チェック）

**masks.png（部位所有権）の契約 — 前景マットと所有権は別概念**

- masks.png は **RGBチャンネルのみ有効**。自身のαは書き出し時に常時255とし、読み込み時は無視する（判定にはいっさい使わない）
- 所有権恒等式は **base.α を基準**に判定する:
  - `base.α > 0` の画素: R+G+B=255（1画素1所有者の排他。境界はソフト値可、ただし合計は常に255）
  - `base.α = 0` の画素: R=G=B=0（所有なし）
- **フェザー帯（0 < α < 255）の画素も必ずいずれかの所有を持つ**。これにより輪郭画素も選択色へ変換され、「アイボリー写真をブラックに変換したら輪郭だけ元色の明色ハロが残る」事故を防ぐ（出力αは base.α のままなのでエッジの柔らかさは維持される）
- 恒等式検査は準備ツール（書き出し前・必須）と `?debug=1`（実行時・任意）の双方で機械検査

**リカラー実行時の合成式（アルファの二重減衰を防ぐ）**

```
出力α   = base.α                       // そのまま透過。再減衰・再適用しない
出力RGB = 革変換×(R/255) + 金具変換×(G/255) + ステッチ変換×(B/255)   // R+G+B=255 なので係数和は常に1
  革     : photoLeatherTone(base.RGB, 選択革色, baseLum, 1.0)   // 第4引数 shadeFactor=1.0 固定（§5-3）
  金具   : metalTone(base.RGB, 選択金具)
  ステッチ: 選択ステッチ色（白 #f5f5f4 / 黒 #1a1a16）の固定色＋輝度による僅かな陰影
```

- 完成チャームビットマップは**アセット解像度（base.png と同寸）で生成・キャッシュ**し、ステージへは全体を等倍率 `N / pxPerMm` で拡縮して `drawImage` する（ステージ座標系でピクセル操作はしない）

**派生値の決定規則（準備ツールが自動算出。実装者裁量を残さない）**

- 輝度式: `lum = (0.2126·R + 0.7152·G + 0.0722·B) / 255`（既存 `index.html` と同一係数）
- **baseLum**: コア画素（`base.α = 255` かつ `masks.R = 255`）の lum を昇順ソートし、0始まり添字 **`floor((n-1)/2)`** 番目の値（下位中央値。例: n=1→添字0、n=2→添字0、n=3→添字1、n=4→添字1）。**コア画素が0件なら書き出しエラー**（そのチャームは派生アセット不成立＝フェーズ0不合格）
- **bboxPx**（革本体の外接矩形）: `masks.R ≥ 128` の画素集合の最小外接矩形
- **fgBboxPx**（前景全体の外接矩形・金具込み）: `base.α > 0` の画素集合の最小外接矩形
- **pxPerMm**: `pxPerMmW = bboxPx.w / sizeMm.w`、`pxPerMmH = bboxPx.h / sizeMm.h`。歪み率 `|pxPerMmW − pxPerMmH| / pxPerMmW ≤ 0.03` を検査。**採用値は pxPerMmW**（丸めず浮動小数のまま記録）

**stitchPaths の契約（stitchMode=fallback のチャームのみ必須）**

```js
stitchPaths: [
  { points: [[x,y], …],      // base.png px座標の折れ線（相異なる2点以上）
    widthMm: 0.8,            // 線幅（mm指定・正の有限値）
    dashMm: 1.8, gapMm: 1.2  // 破線パターン（mm指定・正の有限値）
  }, …
]
```

- **描画座標系**: stitchPaths はアセット座標（base.png px）のまま完成ビットマップへ描画し、線幅・dash・gap は `mm値 × pxPerMm` で**アセットpxに換算**する（ステージ倍率はビットマップ全体の拡縮で一括適用・上記合成方針と一致）
- fallback チャームでは、準備工程で元写真の糸画素を①**革所有（R）としてマスク化**し、さらに②**base.RGB を周辺革色で中和**する（手動インペイント。manual-inpaint レイヤに保存）。①だけでは photoLeatherTone が元画素の明暗を保持するため、選択革色の中に元糸が筋として残る。**白・黒どちらを選んでも元糸の残像が見えないこと**をフェーズ0の必須検査とする（§7-7）
- 実行時の描画順: 革・金具リカラー → stitchPaths を選択ステッチ色で上描き（**革所有領域 `R≥128` でクリップ**）
- 検査（§5-4 書き出し前検査5）: fallback チャームは stitchPaths 非空・全パス点が革所有領域内・各パスが相異なる2点以上・幅/dash/gap が正の有限値・総延長 > 0・クリップ後の描画差分画素 > 0。detect チャームは stitchPaths 空で固定し、`masks.B` 所有画素数 > 0 かつ白黒切替の出力差分画素数 > 0 を検査（「全7種で白黒トグル機能保証」を機械的に担保する）

**チャーム定義テーブル（フェーズ0の成果として全値を確定）**

```js
const CHARMS = {
  horse: {
    label: "ホース",
    base:  "assets/charms/horse.base.png",
    masks: "assets/charms/horse.masks.png",
    sizeMm:   { w: 95, h: 70 },   // 革本体のみ（金具除く）。フェーズ0確定
    bboxPx:   { x, y, w, h },     // 革本体の外接矩形（決定規則は上記）
    fgBboxPx: { x, y, w, h },     // 前景全体の外接矩形（金具込み。配置とクリップ検査に使用）
    pxPerMm:  6.32,               // 決定規則は上記（幅基準）
    threadColor: "dark",          // 元写真の糸色: "dark" | "light"（フェーズ0記録）
    stitchMode:  "detect",        // "detect" | "fallback"（§5-6。noneは無い）
    stitchPaths: [],              // fallback時のみ非空（契約は上記）
    attachmentMode: "photo",      // "photo"=吊り金具が写真に写る | "none"=写らない（§5-5 連結方式の適用判定）
    baseLum:  0.82,               // 決定規則は上記
  },
  // … 7種
};
```

### 5-4. 準備ツール `tools/charm-prep.html`

- ブラウザだけで動く自己完結HTML（`python3 -m http.server` 経由で使用。file:// は canvas 汚染のため不可 — ミニバッグ検証と同じ運用）

**決定的パイプライン（この順で毎回再実行できることが契約）**

```
元写真 → ①回転・クロップ・縮小（長辺≤1200px） → ②自動背景マット（しきい値） → ③manual-alpha適用
     → ④defringe → ⑤自動所有権候補（革/金具/ステッチ） → ⑥manual-owner適用 → ⑦manual-inpaint適用（base.RGB置換）
     → ⑧派生値算出（§5-2決定規則） → ⑨自動検査 → ⑩書き出し
```

**手動補正3レイヤ（いずれも base.png と同寸のPNG。α=0は「無指定」、α=255は「指定あり」の画素）**

| レイヤ | 意味 | 適用 |
|---|---|---|
| manual-alpha.png | R値＝強制する base.α（0–255） | ③で自動マットを画素単位に上書き |
| manual-owner.png | RGB＝強制する所有度（合計255） | ⑥で自動候補を画素単位に上書き |
| manual-inpaint.png | RGB＝置換色 | ⑦で base.RGB を置換（fallback元糸の中和等） |

**自動検査（二段階。循環しない構成）**

【書き出し前検査（⑨。1〜6の全通過が⑩書き出しの条件。結果は prep.json に記録）】

1. 所有権恒等式（§5-2: base.α>0 ⇒ R+G+B=255、base.α=0 ⇒ 全0。違反画素数0）
2. baseLum コア画素 ≥ 1件
3. pxPerMm 歪み率 ≤ 3%（§5-2 決定規則の式）
4. **エッジ帯検査**: **前提条件としてエッジ帯（0 < α < 255）画素数 ≥ 1件**（0件はフェザー契約違反として不合格・分母0を排除）。各エッジ帯画素について最近傍の `α=255` 画素とのRGBユークリッド距離 d を算出し、**d > 32 の画素がエッジ帯全体の 0.5% 未満**（defringe の機械的合否。加えて暗色 #333 / 明色 #eee 背景での目視確認を必須検査として併置 — §7-10）
5. ステッチ機能保証: detect は `masks.B` 所有画素数 > 0 かつ白黒切替の出力差分画素数 > 0 ／ fallback は stitchPaths の有効性一式（§5-2 の検査項目）
6. 転送量: base.png + masks.png 合計 ≤ 900KB

【コミット前検査（7。書き出し済みファイルに対する独立ゲート。合格するまでコミット不可）】

7. **再生成一致（三者照合）**: 準備ツールの再検証モードで、書き出し済みの source-photos 元写真＋prep.json＋manual-*.png を読み込み、次の3照合すべてに合格すること。①**入力照合**: 元写真・manual-*.png の SHA-256 が prep.json 記載値と一致 ②**出力照合**: 書き出し済み base/masks のデコードRGBAハッシュが prep.json の期待出力ハッシュと一致 ③**再生成照合**: パイプライン①〜⑧を独立再実行した結果のデコードRGBA・派生定義値が、書き出し済みファイル・prep.json 記載値と完全一致（比較対象は常に「書き出し済み一式」なので初回生成でも循環しない）。合否は prep.json の `verify` フィールドに追記する

**prep.json（版付きスキーマ。実行時は読まない。派生定義値の正本）**

- `schemaVersion`、ツールバージョン
- 元写真ファイル名と SHA-256、manual-*.png それぞれの参照と SHA-256
- ①の回転・クロップ・縮小値、②の背景しきい値、⑤の金具・ステッチ検出しきい値
- 入力値: sizeMm、threadColor、stitchMode、stitchPaths
- **派生定義値（正本）**: bboxPx・fgBboxPx・pxPerMm・baseLum
- **期待出力ハッシュ**: base.png / masks.png のデコードRGBAの SHA-256（PNGエンコード差に依存しない比較のため）
- 自動検査1〜6の結果値、検査7の `verify` 結果
- **CHARMS テーブルへの転記一致**: `charms.html` の CHARMS 値が prep.json の派生定義値と一致することを `?debug=1` が prep.json を読み込んで機械照合する（§9-0 の受け入れに含む。手転記のミスを検出）

- その他のUI機能: stitchPaths エディタ（頂点打ち＋破線プレビュー）、検証ビュー（暗/明背景合成、マスクオーバーレイ、実寸グリッド、ブラック/アイボリー適用のリカラー試験）
- **手動補正を前提とする**ことで、写真品質のバラつき・自動分類の限界（明色革×白糸、金色金具の彩度など）を人の目で確実に解決する

### 5-5. 合成ステージ（mm 基準座標系）

**実寸校正規則（フェーズ0で7種すべて記録）**

- 実寸 `sizeMm` は革本体のみ（金具除く）。写真側の対応範囲は `bboxPx`（§5-2 の決定規則で自動算出）
- 歪み検査・採用値は §5-2 の決定規則のとおり（幅基準・3%以内）
- 拡縮は等方倍率のみ（縦横別スケールはしない）

**配置式（軸ごとに基準を分離して一意化）**

記号: ステージ中心線 `cx`、丸カン下端 `ringBottomY`（丸カン中心y＋21mm）、革本体間ギャップ `gapMm = 8`、丸カンへの重なり量 `overlapMm = 2`（全チャーム共通の定数。初期値2mm・**フェーズ0の64配置検査前に固定**、以後の変更は§7-11再通過が条件 — 下記「幾何パラメータの固定順序」）

| 軸 | 規則（mm換算はすべて当該チャームの pxPerMm を使用） |
|---|---|
| y（1点/2点共通） | **前景上端**（`fgBboxPx` 上端）が `ringBottomY − overlapMm` に一致（吊り金具が丸カンに少し重なって通って見える） |
| x（2点表示） | 左チャーム: **革本体右端**（`bboxPx` 右端）が `cx − gapMm/2` ／ 右チャーム: **革本体左端**が `cx + gapMm/2`。x配置に fgBbox は使わない |
| x（1点表示） | 革本体（`bboxPx`）の中心xが `cx` に一致 |

- y は前景基準（金具込み）・x は革本体基準、と**軸ごとに基準を分けることで一意に決まる**（吊り金具のx位置は丸カン直下に来ないことを許容する。厳密な物理接続の再現はスコープ外で、組み合わせ・配色の確認という目的を優先）
- チャームの向きは**写真のまま（頭が左向き）を左右共通**とする。左右反転はしない（革製品は表裏があるため反転表示は実物と乖離する。§11-2）
- 接地影: 不要（吊り下げ表示のため）。輪郭の自然さは defringe とフェザーで担保

**LAYOUT 定義（幾何の正本）と固定順序（64配置検査を無効化させない）**

- ステージ幾何は単一の `LAYOUT` 定義（コード上の1オブジェクト）に集約して記録する: ステージ寸法（mm）、描画解像度 N、丸カン中心座標（**`ringCenterXMm = ステージ幅/2`、`ringCenterYMm = 上マージン10 + 半径21 = 31mm` の数値で固定**）、`gapMm`、`overlapMm`、金具なし写真の連結方式（隙間を空ける／簡易連結を描画する — 適用条件・座標式・描画順・描画境界まで）
- 写真金具の有無はチャーム定義の **`attachmentMode`**（`"photo"`＝吊り金具が写真に写っている ／ `"none"`＝写っていない→LAYOUT の連結方式を適用）として記録し、簡易連結の適用条件をチャーム単位で機械判定できるようにする（フェーズ0で7種すべて記録）
- 以下は**64配置クリップなし検査（§7-11）を実行する前に確定**する: LAYOUT の全値、チャームの向き、1点表示の配置（§11-1・11-2 の回答が前提）
- **64配置検査の対象は「チャーム前景（fgBbox）∪ 簡易連結を採用した場合はその描画境界」の和集合**とする（事前計算と実描画の境界を一致させる）
- **確定後に LAYOUT のいずれかを変更した場合**（フェーズ1のテイスト確認による調整を含む）**は、ステージ寸法と全64配置を再計算し、フェーズ0ゲート（§7-11）を再通過してから先へ進む**

**ステージ寸法（仮値 → フェーズ0で機械検証）**

- 仮値: 革寸法ベースの最大組み合わせ **ホース×ホース = 95 + 8 + 95 = 198mm** ＋左右マージン各11mm → **幅220mm**。高さ: 上マージン10 + 丸カン42 + 重なり−2 + 前景最大高（仮: 金具込み90） + 下マージン15 → **155mm**
- **フェーズ0の確定値（fgBboxPx / bboxPx / pxPerMm）を用い、全64配置について上記配置式で前景境界を機械計算し、ステージ内に収まる（クリップなし）ことを検査**する。仮値で収まらなければステージ寸法を更新し、§9-1 の受け入れと連動させる（写真内金具の張り出しを含めた検証であり、革寸法だけの机上計算では確定しない）
- 描画解像度: `1mm = N px` の単一定数（初期値 N=6 → 1320×930px。フェーズ1の性能実測で確定）
- 丸カン: ステージ上部センター固定（外径42mm厳守）

### 5-6. リカラー・ステッチ・金具

**革リカラー**: `photoLeatherTone(base.RGB, 選択色, baseLum, 1.0)` を革所有画素に適用（**全呼び出し箇所で4引数・shadeFactor=1.0 固定**・§5-3。代表 baseLum × 24色全部で出力RGBが有限値であることを検査項目とする）。左右チャームで独立した24色（既存パレット・グループUI流用）

**ステッチ（白/黒トグル・全7種で機能保証）**

- stitchMode は **detect / fallback の2種のみ（none は設けない）**。7種すべてで白黒トグルが必ず機能する
- `detect`: 準備工程で写真のステッチ画素を検出してマスク化（糸色極性 `threadColor` に応じ、暗糸なら低輝度側・白糸なら高輝度側を検出）。実行時は**選択色（白/黒）を問わず検出画素を明示的に塗り直す**（「黒選択時は原画のまま」という元糸色依存の仕様は廃止）
- `fallback`: 写真の糸と革のコントラストが低くマスク化できないチャームに適用。破線パスを手動定義し、革所有領域でクリップして白/黒で上描き（ミニバッグ実績方式）
- 選定はフェーズ0で写真ごとに判断し、テーブルに記録

**金具（銀/金トグル）**

- 丸カン: 準備工程で生成した透過PNG（`ring-silver.png` / `ring-gold.png`・42mm外径の共通基準枠に正規化・中心一致）の差し替え。切替で位置・サイズ不変（§9-8）。実行時の背景除去はしない（§5-3）
- チャーム側の吊り金具・飾り金具（ホースシューのスタッズ等）: **写真に見えている金属はすべて金具マスクに含め、`metalTone()` で選択色に連動変換する**。これをフェーズ0の**非免除合格条件**とする（§7-8）
- 手動ブラシ補正（§5-4）を使っても金具マスクを正しく塗り分けられない写真は**再撮影依頼**とする。「画像から金具を除去する」案は**採用しない**（単純なα消去はスタッズ跡が穴になり吊り金具では連結構造も破壊される。インペイント修復は準備ツールのスコープ外）。「写真側は銀のまま・丸カンだけ金」という**固定色金具の混在も不可**（画面とサマリー文の不一致を仕様レベルで排除）

### 5-7. 性能・メモリ設計

- 実行時のピクセル走査はリカラー変換のみ（背景除去・マスク生成は準備工程で完了済み）
- 派生アセットは選択時に遅延ロード。**転送量上限: base+masks 合計 ≤ 900KB/チャーム**（§5-4 書き出し前検査6としてフェーズ0で機械検査。超過時はPNG最適化または解像度の見直し）
- リカラー結果は「チャーム×革色×金具×ステッチ」キーでキャッシュ（LRU・上限8エントリ）。**LRU退避時は `ImageBitmap.close()` 等で明示解放し、9件目生成時の退避→解放→再生成の動作を受け入れ試験で確認**する（§9-12）
- **ピークメモリの概算対象**を「デコード済み派生アセット（全7種保持で概算80MB: 1200²×4B×2枚×7種）＋LRU完成ビットマップ8エントリ＋作業ImageData＋ステージcanvas」と定義し、フェーズ3で概算値を報告する。モバイルSafariでのメモリ挙動（タブ再読込の発生有無）を実機確認する
- ステージ再描画は `drawImage` 合成のみ
- **性能基準と計測方法**:
  - キャッシュ済み切替: 入力イベント発火→描画完了（最終 `drawImage` 直後）を `performance.now()` で計測し、**連続10回の中央値 ≤ 300ms**。対象: macOS Chrome 最新・iOS Safari（実機1機種以上）
  - 初回選択（アセットロード込み）: **HTTP warm cache（2回目以降のアクセス相当）で、相異なる2チャームを同時ロードする条件に固定し ≤ 1500ms**、その間は既存の「読み込み中」表示。cold cache（初回訪問）はローディング表示があれば基準対象外と明記
- **非同期の追い越し対策**: 描画に世代トークンを付与し、素早い連続切替時に古い非同期結果（画像ロード完了等）が最新状態を上書きしないことを保証する（§9-9）

## 7. 写真素材の受け入れ要件（フェーズ0チェックリスト）

手元にある7種の写真を、以下の観点で検証してから派生アセット生成に入る。**「免除」列が「不可」の項目は例外承認で通過できない**（§8 フェーズ0ゲート）。

| # | 要件 | 免除 | 満たさない場合の対処 |
|---|---|---|---|
| 1 | チャーム単体で全体が写っている（見切れなし） | 不可 | 再撮影依頼 |
| 2 | 正面・吊り下げ時と同じ上下向き | 可 | 回転補正で吸収可能か個別判断 |
| 3 | 背景が無地でチャームと分離可能（白/ライトグレー推奨） | 不可 | 準備ツールのしきい値調整＋手動ブラシ補正で解決（それでも不可なら再撮影） |
| 4 | チャーム部分の解像度が長辺 600px 以上 | 不可 | 拡大は不可。再撮影依頼 |
| 5 | 7種の照明条件が概ね揃っている（極端な色かぶり・強い影がない） | 可 | baseLum 正規化で吸収 → 不可なら再撮影 |
| 6 | 革色が明るめ単色（アイボリー等）だと濃色変換に最有利 | 可 | 濃色ベース写真は変換品質を個別確認 |
| 7 | **ステッチの糸色（白/黒）を記録**し、革とのコントラストで stitchMode を判定。fallback 選定時は stitchPaths の定義＋**元糸RGBの中和（manual-inpaint）**を実施し、**白・黒どちらの選択でも元糸の残像が見えない**こと | 不可 | 低コントラストは fallback（手動破線パス＋元糸中和）に切替 |
| 8 | **見えている全金具（吊り金具・スタッズ等）が金具マスクで選択色に変換できる** | 不可 | 手動ブラシ補正で解決 → 不可なら再撮影依頼（除去・固定色混在は不可・§5-6） |
| 9 | 撮影歪み: pxPerMm 歪み率3%以内（§5-2 決定規則） | 不可 | 超過時は実寸再確認 or 再撮影 |
| 10 | **§5-4 の書き出し前検査1〜6に全通過（通過するまで書き出し不可）＋コミット前検査7（再生成一致）に合格（合格するまでコミット不可）**＋暗色/明色背景での輪郭の目視確認 | 不可 | 準備工程をやり直し |
| 11 | **幾何パラメータ固定（§5-5）のうえ、全64配置のクリップなし検査**（確定値による機械計算） | 不可 | ステージ寸法を更新して再検査 |

**フェーズ0の成果物**: ①7種の派生アセット一式（base/masks PNG＋prep.json＋manual-*.png）、②丸カン透過PNG（ring-silver/gold）、③チャーム定義テーブル全値（sizeMm確定値・bboxPx・fgBboxPx・pxPerMm・threadColor・stitchMode・stitchPaths・baseLum）、④素材検証レポート（チェックリスト判定＋例外事項＋64配置検査結果＋書き出し前検査1〜6・コミット前検査7の記録）

## 9. 受け入れ基準

0. **派生アセット検査**: 7種すべてが §5-4 の書き出し前検査1〜6＋コミット前検査7（再生成一致）に通過している（フェーズ0成果の再確認）。**CHARMS テーブル値と prep.json 派生定義値の転記一致を `?debug=1` の機械照合で確認**
1. **64通り配置スモーク**: 左右 8×8 全組み合わせ（同一チャーム同士・なし×なし含む）がエラーなく表示され、**前景（金具込み）がステージ内に収まる（クリップなし）**。ホース×ホース（革幅ベース最大198mm）を必須確認
2. **実寸比率**: チャーム同士の大きさ比率が実寸どおり（例: ホース幅:ホースシュー幅 ≒ 95:46。debug グリッドで検証）
3. **固定検証セット**: 7種それぞれ × 革色{ブラック, アイボリー} × ステッチ{白, 黒} × 金具{銀, 金} の56ケース（片側表示）で、マスク品質・白飛び・ステッチ視認性（fallbackチャームは**元糸の残像なし**を含む）・金具変換を目視確認
4. **応答性能**: §5-7 の計測方法で中央値 ≤300ms（キャッシュ済み切替）、初回選択（warm cache・相異なる2チャーム同時ロード）≤1500ms＋ローディング表示
5. **サマリー一致**: 左右独立カラー・【なし】各状態でサマリー文・コピー文面が表示と完全一致（§6-3 の3形態すべて）
6. **【なし】挙動**: §4-2 の表のとおり（センター寄せ・丸カンのみ・スウォッチ/ステッチ無効化）
7. **輪郭品質**: 暗色革（ブラック #41413d）選択時・暗色背景 debug 表示で、輪郭に白ハロ・フチ欠けがない
8. **丸カン切替**: 銀⇔金の切替で丸カンの位置・サイズが変わらない
9. **連続操作**: 素早い連続切替で描画結果が最新の選択状態と一致する（世代トークン）。アセットロード失敗時は既存 `index.html` 同様のエラーメッセージを表示する
10. **レスポンシブ**: スマホ（375px幅）で操作・表示が崩れない
11. **既存無影響**: `index.html` に変更がない（フェーズ4のナビ追加時は追加リンク以外の差分ゼロ）
12. **メモリ挙動**: 完成ビットマップの9件目生成時に LRU 退避→`ImageBitmap.close()` 実行→退避済みエントリの再選択で正しく再生成されること。モバイルSafari 実機でタブ再読込が発生しないこと
13. **photoLeatherTone 有限値検査**: 7種の baseLum × 24色の全組み合わせで出力RGBの全成分が有限値（NaN/Infinity なし）であること（フェーズ1の必須単体検査として実施し、フェーズ3で再確認）

## 10. リスクと対策

| リスク | 対策 |
|---|---|
| 写真の撮影条件バラつき（スケール・照明・背景） | スケールは実寸mm基準の等方正規化＋3%歪み検査（§5-2）。照明は baseLum 正規化。背景・マスク品質は**準備工程の手動補正で人が確定**してからコミット（実行時リスクなし） |
| 輪郭の白ハロ（JPEG背景の色かぶり・フェザー帯の元色残り） | defringe＋「フェザー帯も所有を持つ」恒等式（§5-2）を契約化し、暗色背景合成の検証を準備ツールと受け入れ基準（§9-7）の両方に置く |
| ステッチのコントラスト不足でマスク化不能 | stitchMode=fallback（stitchPaths契約・§5-2）に切替。noneは無いため白黒トグルは常に成立 |
| 濃色リカラーの白飛び | photoLeatherTone のハイライト保護（実績値 lum≥0.94・上限0.38）を初期値に、フェーズ1で実写チューニング |
| 金色金具の彩度が革と近く自動分類しにくい | 準備工程の手動ブラシ補正で確定（自動分類の精度に依存しない）。それでも塗り分け不能なら再撮影（除去はしない・§5-6） |
| 実寸データの誤り | フェーズ0で実物と突き合わせ確定＋pxPerMm歪み検査。以降は定義テーブルの1箇所修正で全体反映 |
| 吊り金具の写り込みが7種で不統一 | フェーズ0で7種の写り方を確認し連結表現を統一（§5-5）。全金具変換の非免除合格条件（§7-8）で色不整合は仕様レベルで排除 |
| 写真内金具の張り出しでステージからはみ出す | 前景（fgBbox）ベースの64配置クリップなし検査（§5-5・§7-11）で機械的に検出し、ステージ寸法を更新 |
| 派生アセットの再生成不能（手動補正の属人化） | prep.json＋manual-*.png の版付きスキーマと決定的パイプライン（§5-4）で全状態を保存し、準備ツールの読込・SHA照合・再実行機能＋再生成一致検査（自動検査7）で機械的に担保 |
| fallback元糸の残像（革リカラー後に糸の筋が残る） | 準備工程の manual-inpaint による元糸RGB中和＋白黒双方の残像なし必須検査（§5-2・§7-7） |
| 準備ツールの実装コスト | 既存 `extractKeyRingAsset()`・ステッチ検出の流用で初期実装を短縮。ツール自体は使い捨てでなくスワン等の将来追加にも使う資産になる |

## 11. 確認ポイント（レビューのお願い）

1. **【なし】1点時のセンター寄せ**: 片方だけの場合に真下センターへ移動する仕様（§4-2）でよいか？（左右位置のまま表示する案もあり）**※配置に影響するためフェーズ0の64配置検査前に回答が必要（§5-5・§8）**
2. **チャームの向き**: 左右とも写真のまま（頭が左向き）でよいか？ 右側だけ反転して向かい合わせにする案は、革の表裏が実物と変わって見えるため非推奨としたが最終判断を仰ぎたい。**※同上、64配置検査前に回答が必要**
3. **ステッチ初期値**: ホワイト想定（実物の標準仕様に合わせる・旧計画書の方針踏襲）でよいか？ 既存ドーナツ版はブラック初期のため、ページ間で初期値が異なることになる
4. **チャーム選択UI**: プルダウン（第一案）でよいか？ 写真サムネイルのグリッド選択の方が直感的だが、実装量とスマホでの場所を取る
5. **初期表示の組み合わせ**: 仮案「左 ホース × 右 キャット」でよいか？
6. **左右同一チャーム**: 「選択可能」を仕様とした（§4-1。ステージ寸法も同一チャーム前提で計算済み）。不可に変える場合もステージ設計はそのまま成立する
7. **写真素材の共有方法**: 手元の7枚をリポジトリに配置いただくか、こちらで配置するか（フェーズ0の起点）。また元写真は公開リポジトリに置かれる点も問題ないか
